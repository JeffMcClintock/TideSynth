Status: `TODO` · `DOING` · `IN-REVIEW` · `DONE` · `BLOCKED` / `BLOCKED(<id>)` ·
`NEEDS-JEFF` · `WONTFIX`

- `IN-REVIEW` = work complete, PRs open (linked in the row). A run never sets
  `DONE` on its own fresh work; `DONE` is set when every linked PR has merged,
  by Jeff or by a later run that observes it.
- `BLOCKED(<id>)` = blocked until `<id>` is DONE. **Eligibility lives in this
  column alone** — section prose never overrides it.
- `NEEDS-JEFF` rows should carry a `Default in effect:` and a `Decide-by:` line
  (template in [docs/decisions.md](docs/decisions.md)), so an unanswered
  question cannot silently become the answer.
- `WONTFIX` = considered and declined, with the reasoning in the row. Do not
  re-file it.

Platform: `any` · `win` · `mac` · `linux`

New items state three things, tersely: **Scope** (files/dirs), **Accept** (a
command or observable that proves it done), **Size** (fits one session, or
names its stages). Anything longer than a few lines lives in `docs/<id>.md`
with the row pointing at it. An agent that cannot state an item's acceptance
check before starting must skip it and mark it `NEEDS-SPEC` rather than guess.

Update this file at the end of every run. An item left in `DOING` with no
matching JOURNAL entry means a previous run died — reset it to `TODO` and note
that in the journal (claims younger than 24h are presumed live; see the run
prompt).

Both sites are one function each; the work is small, the format choice is not. **Deliberately not implemented unsupervised:** the rest of today's fixes were behaviour, this one is compatibility — a preset written by the first implementation must stay readable by every later one. **DESIGN ANSWERED BY JEFF 2026-08-17 — the three questions below are settled, so this row is specified and no longer needs his input to start:** **(1) A new document implies a rebuild of the DSP graph, and SynthEdit already handles that — fade-out → teardown → reconstruction → fade-up.** So restore drives the existing mechanism rather than inventing one. **(2) A host preset change MAY modify the rack** — treat it as loading a brand-new document; anything can change. **(3) All state lives in the preset** — which settles "plug-in state vs a referenced user file" in favour of the preset, and is what makes (2) coherent. **BLOCKED IN PRACTICE BY S12, discovered while reading the path ruling (1) points at: there is no DSP graph to rebuild** — TIDE's processor is a silent stub. The restore path here can be written and will be correct, but its DSP half cannot be exercised or verified until S12 lands, so **take S12 first**. Original row follows. **TIDE never saves or restores the user's rack — the patch is lost the moment a project is reloaded.** Found 2026-08-17 (macos, interactive) while measuring U1c's `rackMode`-on-load follow-up; the follow-up turned out to be unanswerable because **nothing loads a document at all**. **Evidence, three cheap steps:** (1) the saved VST state is **250 bytes of base64** for a project containing a placed List Entry in a rack (`GetTrackStateChunk` via ReaScript) — a document with a module in it cannot fit; (2) decoded, the `.rpp`'s VST block is literally `<Preset><Param id="1" val="0"/><Param id="0" val="0"/></Preset>` — `controllerPtr` and `chunk`, both zero; (3) **save → close → reopen → the module is gone**, the plug-in draws an empty rack (rails present, because rack mode is set at document creation). Verified visually. **Mechanism, so this is actionable:** TIDE's XML already declares the parameter this needs — `<Parameter id="1" name="chunk" ignorePatchChange="true" datatype="blob"/>` in `SynthEditSem/SynthEdit.cpp` — and **nothing ever writes or reads it**; `TideApp::InitInstance` unconditionally calls `createNewDocument()` + `OnNewDocument()`, so every instance starts empty by construction. `MpController`/`DawPreset` serialise *parameter values*, which is exactly the two-param XML observed. The document already has serialisers: `CSynthEditDocBase::ExportXml` / `ImportXml`. **Why this is an architecture difference, not a regression:** in a normal SynthEdit-exported plug-in the document IS the product — baked in at export, so the chunk need only carry knob values. TIDE inverts that: the document is what the user edits at runtime, so it must ride in the state, and nothing before TIDE needed that. **Scope** `SE16/SynthEditSem/` (ALLOWED) for the save/restore hooks; the serialisers are in `SynthEditLib`. **Accept** place a module, save the host project, reopen it, and the module is still there — the same three-step test above, passing. **Questions that need Jeff before the design settles:** does restoring a document have to rebuild the DSP graph (and if so, is that safe mid-session)? should a host patch/preset change reload the rack, or only project load? and does the rack belong in the plug-in state at all, or in a user-visible file the state merely references? **Size** a real session, probably more; do not start it at the end of one. **This blocks the R-series** — a synthesiser that cannot save its patch is not shippable, which turns "there is nothing to ship" into one concrete thing to build. |
