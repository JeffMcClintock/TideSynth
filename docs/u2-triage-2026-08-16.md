7.45/macOS-arm64, the U1a build of `TIDE_VST3.vst3`, all five repos at that

## The headline

**The view renders and the model layer is correct on both platforms; what is
broken is input plumbing on mac and two bad defaults everywhere.** Nothing
found here re-opens U1a. The four symptoms map to four rows:

| U2 symptom | verdict | root cause | row |
|---|---|---|---|
| (2) wheel dead | **mac-only, FIXED this session** | dispatch commented out in the mac backend | **U2a** — IN-REVIEW, [gmpi_ui#7](https://github.com/JeffMcClintock/gmpi_ui/pull/7) |
| — (new) middle-pan dead | mac-only, found during triage | `otherMouse*` handlers absent | **U2b** |
| (4) corner-anchored canvas, odd re-anchor on resize | cross-platform, root-caused to a line | `TopView::centerPos` defaults `{0,0}`; TIDE never sets it | **U2c** |
| (3) placed control draws adorner-only | cross-platform, **the remaining unknown** | panel draws nothing; standing hypothesis: no skin resources staged | **U2d** |
| (1) drag-drop places nothing | **not a code defect** | click-arm → click-place is the design; the drag gesture was never the mechanism | UX decision, recorded below |

## (2) → U2a: the mac wheel — root-caused, fixed, verified

`gmpi_ui/backends/DrawingFrameMac.mm scrollWheel:` (`:802-822` before the fix)
received the event, computed `deltaX`/`deltaY` and the flags — and then did
nothing: **both dispatch lines were commented out as `// TODO`.** The
VST3-level fallback (`SEVSTGUIEditorMac.h:24 onWheel`) returns `kResultFalse`,
so both layers discarded the event. This is exactly why the Windows re-test
could not reproduce (2): `DrawingFrameWin.cpp`'s `WM_MOUSEWHEEL` →
`inputClient->onMouseWheel(p, flags, zDelta)` path was always finished.

The fix mirrors the Windows shape using the `inputClient` the mac frame
already holds (and already uses for `onPointerDown/Move/Up` — which is why
clicking always worked while the wheel did not): convert the mouse position
with the file's own `mouseToGmpi`, scale deltas by the 120-per-notch
convention, flag `ScrollHoriz` for `deltaX`.

**Verified live** in REAPER on a fresh process: plain wheel pans the canvas
both directions; Ctrl+wheel zooms (visible canvas area grew with a finer
grid); the module browser list scrolls, revealing entries below the fold
(Monostable, NAND/NOR/NOT/OR Gate…) that were **unreachable by any input**
before — TIDE hides scrollbars (`TideApp.cpp`'s no-op `hscrollBar`/`vscrollBar`
lambdas exist only to keep `TopView::onMouseWheel` from short-circuiting), so
until this fix the wheel hole meant *no navigation at all* on mac.

## (new) → U2b: middle-button grab-pan never reaches the view on mac

Found while confirming U2a. `SE2::TopView` implements middle-drag grab-pan
(`ViewBase.h`: `isPanning`, `panRefMouse`/`panRefCenter`, `onPointerDown`
intercepts `ThirdButton`), but the mac backend implements only
`mouseDown / mouseUp / mouseDragged / mouseMoved / rightMouseDown /
rightMouseUp / mouseEntered / mouseExited / scrollWheel` — **no
`otherMouseDown:/otherMouseDragged:/otherMouseUp:` exist**, so the middle
button never enters GMPI. Three small handlers, same shape as the existing
pairs. (Whether the *Windows* gmpi_ui backend routes `WM_MBUTTON*` was not
checked — verify before assuming parity.)

## (4) → U2c: one uninitialised default explains the corner anchor AND the Windows "every module lands on the same point"

- `TopView` pan/zoom ground truth is `centerPos` (document coords) —
  **default `{0,0}`** (`SynthEditLib/modules/se_sdk3_hosting/ViewBase.h`).
- TIDE never calls `setCenter`/`setPanZoom` — grep of `SynthEditSem/` finds
  zero call sites.
- So the viewport centres on the canvas's **top-left corner**: the canvas
  fills only part of the pane, dead grey fills the rest — **this is the §6
  "canvas offset / dead strip", now a named pan default rather than a drawing
  bug** (the two boxes see the dead area on different sides only because
  their windows are shaped differently around the same corner).
- `arrange()` recomputes the transform around the same `centerPos` on every
  resize — the "odd re-anchoring" both boxes recorded.
- Double-click insert goes `OM_INSERT_MODULE_AT_VIEW_CENTER` →
  `p->AddModule(moduleId, view->getCenter())` (`SynthEditGui.cpp`) and
  `TopView::getCenter()` returns `centerPos` → **inserts land at `{0,0}`**,
  which is precisely the Windows entry's *"every later module landing on that
  same point"* at the canvas origin.

Fix is one line in ALLOWED `TideApp.cpp` (`OpenView`, after `setDocument`):
set the centre to the canvas midpoint or content bounds. **U1c owns the final
answer to what "home" is for a rack**; U2c is the sane default until then.

The Windows entry's *"start triage from (3)+(4) as one geometry cause"* was
half right: they are adjacent but distinct — (4) is this pan/insert default,
(3) is below and is not fixed by any amount of panning.

## (3) → U2d: the placed control draws only its resize adorner — the remaining unknown

Reproduced deterministically on both boxes: insert List Entry → properties
pane fully correct (pins, parameters, Appearance=Combo Box) → canvas shows
**only the ResizeAdorner around a degenerate rect**. Jeff identified the
adorner live on mac ("blue rectangle with white circles — only the resizer");
Windows saw the identical shape at literal zero size. Model right, view
empty: the break is in panel measure/draw, not the document.

**Standing hypothesis — missing panel/skin resources.** The panel pipeline is
skin-driven: `ContainerView.cpp:25` reads the skin name from the presenter
context; SkinMgr + GmpiResourceManager load skin data from disk. The mac
`TIDE_VST3.vst3` bundle stages **no Resources at all** — binary, Info.plist,
signature, nothing else — where `SynthEditCL.app` stages
`fonts`/`skins`/`templates`/`Prefabs` (P6's record). Zero skin data → nothing
to draw → zero measure → adorner-only.

- **Falsifier, cheap:** stage the default skin into `Contents/Resources`,
  restart the host (see the reload lesson below), insert a List Entry — it
  draws, or the hypothesis dies.
- **Ruled out:** P11's stale-module-database trap — the Windows session hit
  it first, fixed it, and (3) still reproduced.
- **Open:** whether the Windows build stages skins. If it does, a failing
  falsifier needs a second mechanism, so check that first.

## (1) → not a defect: placement is click-arm → click-place, by design

`SynthEditGui.cpp`'s own comment block: clicking a module in the browser
fires `OM_DRAG_NEW_MODULE` → `view->DragNewModule(id)` arms the view
(`draggingNewModuleId` + `setCapture`), and *"the next click on the editor
strip drops the module via ViewBase's existing onPointerDown drag-receive
path."* **Proven live on mac:** single-click "List Entry" in the browser,
single-click the canvas at an arbitrary point → the module was placed at
exactly that point (properties pane populated on the spot).

What both boxes reproduced as "(1) drag-drop places nothing" is that the
**press-drag-release gesture users try first does not place** — the arm fires
on the browser click, and the drop path listens for the next pointer-*down*;
a release over the canvas is not a drop. That is a UX decision, not a
platform bug: either the click-click design stands (a tooltip/cursor cue
would help — `dragInProgress` cross-cursor is Win32-only today), or the
drag-receive path also accepts drop-on-pointer-up when armed-and-moved.
**Default in effect: the design stands.** Jeff decides; nothing blocks on it.

Also correct-and-not-bugs: DSP/conversion modules (Moog Filter, Volts To
List2) showing no panel is panel-view semantics; and one mid-triage probe
"inserted the wrong module" only because the browser list had scrolled under
a stale screen coordinate — operator error, recorded for honesty.

## Operational lessons (cost this session real time)

1. **A host keeps a VST3 module mapped after FX-remove.** Remove instance →
   replace bundle on disk → re-add loaded the OLD code, and the first
   post-fix wheel test "failed" for that reason alone. A full host restart is
   required to pick up a replaced binary. Budget it into every
   edit-build-verify loop.
2. **`reaper-vstplugins_arm64.ini` is not a live mirror of REAPER's plugin
   registry** — it survived a clear-cache re-scan *and* a clean quit
   byte-identical (mtime stuck at 15:23 through 16:25), while the FX browser
   and `TrackFX_AddByName` showed the new identity throughout. The previous
   mac journal entry's "the ini rewrites when REAPER exits" was an overclaim
   — corrected here. While the app runs (and apparently even after it exits),
   **the FX browser is the only authority.**
3. `REAPER -nonewinst <script.lua>` (from the U1a-verification session)
   remains the pattern for API-level answers without screen control.
4. This box's REAPER support dir has `reaper.ini` and `reaper-reginfo2.ini`
   **owned by root** (dated Sep 2025) — REAPER cannot persist its own
   preferences here. Jeff was told live; it is his machine's quirk, not
   TIDE's, and nothing in this triage depends on those files.
